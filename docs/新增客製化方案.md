## 這件事刻意不做抽象

新增方案的做法就是**複製一份現有的最接近的方案再改**，不要為它蓋通用機制。理由：

- C 和 D 建立於 `2026-04-27`（相隔 12 分鐘），到 `2026-10-06` 為止新增方案數量為 **0**。抽象的回報與新增頻率成正比，而實測頻率接近 0。
- 真正會重複改到四份的部分（欄位元件、草稿儲存、送出後唯讀）**已經共用**了，見
  [`client/src/components/CustomForm*.tsx`](../client/src/components)（五個欄位元件）與
  [`client/src/lib/customFormSubmission.tsx`](../client/src/lib/customFormSubmission.tsx)。
- B 的塔羅選題介面（分類 tab、19 個主題、每題五條占卜項目、選了會改訂金價）在商業上就只有塔羅會用，通用化之後只會有一個使用者。

所以**這份清單本身就是替代抽象的工具**。照著走，不要發明新結構。

## 必須改的地方

順序建議照這個表，因為第 1 項是其他項的來源。

### 1. `shared/const.ts`

```ts
export const CUSTOM_XXX_PRODUCT_ID = "xxx-crystal-deposit-product";
export const CUSTOM_PRODUCT_IDS = [..., CUSTOM_XXX_PRODUCT_ID];
```

**漏掉的後果最嚴重**：這個陣列是以下自動行為的唯一開關，少了它，新方案會變成一個「看起來正常、實際半壞」的商品——

| 檔案 | 少了會怎樣 |
|---|---|
| [`server/inventoryDb.ts`](../server/inventoryDb.ts) `NON_INVENTORY_PRODUCT_IDS` | **會扣庫存**，而客製商品沒有庫存，等於直接扣成負的 |
| [`shared/checkoutFees.ts`](../shared/checkoutFees.ts) `isCheckoutFeeExemptProduct` | **會收運費** |
| [`server/reviewDb.ts`](../server/reviewDb.ts) `isReviewableProductId` | **會被顧客評價**（訂金商品不是完成品） |
| [`server/routers/products.ts`](../server/routers/products.ts) `topSellers` | **會出現在首頁熱銷** |
| [`client/src/pages/Checkout.tsx`](../client/src/pages/Checkout.tsx) | 結帳不走客製分支，會要地址、要選超商 |
| [`server/customFormReminders.ts`](../server/customFormReminders.ts) | 表單未填不會發 LINE 提醒 |
| [`client/src/pages/AdminInventory.tsx`](../client/src/pages/AdminInventory.tsx) | 會出現在後台庫存列表 |

## 不要做的事

### 不要把 `custom` 加進 `AdminProducts.tsx` 的 `CATEGORY_OPTIONS`

[`client/src/pages/AdminProducts.tsx`](../client/src/pages/AdminProducts.tsx) 的 `CATEGORY_OPTIONS` **刻意**沒有 `custom`，雖然：

- 後台編輯表單已經有客製分支（把「功效說明」換成「下單流程 + 注意事項」）
- server 的 `ProductInputSchema` 是 `category: z.string().min(1)`，不是 enum，任何字串都收
- `id` 也是後台可指定的

所以「只差一個下拉選項」是錯覺。加上去之後店長建出來的商品**不會在 `CUSTOM_PRODUCT_IDS` 裡**，於是會扣庫存、會收運費、會被評價、會上首頁熱銷——而且外觀完全正常。

要開放後台建立客製商品，得先把第 1、2、7 項改成資料驅動，其中第 7 項還會牽動
[`shared/checkoutFees.ts`](../shared/checkoutFees.ts) 的 `calcCheckoutFees`——那是前後台共用的**同步純函式**，改成讀 DB 就得變 async，而它是防止「前端算一套、後端算另一套」的機制。**動它等於動金流計算。**

### 不要在 `ensureProductsTable()` 加無守門的一次性補值

歷史上有一段無條件 `UPDATE products SET howToUse = ...`，而 `tableEnsured` 是 module-level 變數，所以**每次 cold start 都會重跑**，把店長在後台改過的「下單流程」蓋掉，錯誤還被 `catch {}` 吞掉。已於 `a141610` 移除。

同一個函式裡其他補值都有 `AND ... IS NULL` 守門，只補空值。**要加補值就照那個樣子加。**

## B 方案（塔羅）額外的地方

只有需要「選購方案 / 選題組」時才會碰到：

| 檔案 | 內容 |
|---|---|
| [`shared/tarotPricing.ts`](../shared/tarotPricing.ts) | 19 個主題的 id／名稱／原價／折扣價，與 `getTarotDepositPrice` |
| [`shared/tarotRequirements.ts`](../shared/tarotRequirements.ts) | `TAROT_GROUP_SPEC`：每個組合的「占卜前需提供」文字 **與** 表單欄位定義 |
| [`client/src/lib/productOptions.ts`](../client/src/lib/productOptions.ts) | `requiresDetailSelectionBeforeCart`：強制先在商品頁選題才能加入購物車 |
| [`client/src/pages/ProductDetail.tsx`](../client/src/pages/ProductDetail.tsx) `:44` | `tarotReadingCategories`：商品頁價目表 |

主題是透過 `orderItem.purchaseOptionId = "tarot-topic:<id>"` 記在訂單上，表單再用
`getTarotTopicByOptionId` 讀回來並鎖定，顧客不能改。

> ⚠️ **塔羅價格存在兩個地方**：`tarotPricing.ts` 的 `TAROT_TOPICS`（實際算錢）與
> `ProductDetail.tsx` 的 `tarotReadingCategories`（商品頁顯示的價目表）。
> 兩邊目前 19 筆一致，但**調價要改兩處**，漏一邊就是「商品頁寫 899、實際收 999」。

### 塔羅欄位要加減時

改 [`shared/tarotRequirements.ts`](../shared/tarotRequirements.ts) 的 `TAROT_GROUP_SPEC` 就好，渲染、必填驗證、寫進訂單備註三者都從它衍生。
`requirements`（商品頁對客人的承諾）就放在同一個物件裡，所以不會改了欄位忘了改承諾。
[`server/tarotRequirements.test.ts`](../server/tarotRequirements.test.ts) 會再擋一次。
